## October 25: the repeated hour and operation without a network

The transition implemented in the firmware is **01:00 UTC**, when Vilnius
changes from UTC+3 to UTC+2: **03:59:59 becomes 03:00:00**.

`log/2026-10-25.log` provides these boundary observations:

| UTC / line | Evidence |
|---|---|
| 00:43:26 / 479 | Last redraw before the transition, partial for IAQ; expected footer minute `03:43` |
| 00:53:15.060 / 505 | SNTP answer 35, `system_minus_sntp_ms=-1` |
| 00:59:01.746 / 519 | SCD41 summary, uptime 122,793,603 ms |
| 01:00:01.746 / 521 | Next SCD41 summary, uptime 122,853,603 ms: exactly 60 s later |
| 01:13:26.007 / 550 | First subsequent redraw, full for the accuracy status change; expected footer minute `03:13` |
| 01:13:27.851 / 554 | Refresh returns `epd_draw_error=0 status=0` |
| 01:53:15.070 / 637 | SNTP answer 36, `system_minus_sntp_ms=-1` |

There is **no SNTP answer at 01:00**, no one-hour correction and no reboot.
UTC and monotonic uptime continue through the boundary, and the recorder
does not open new files at it. It rotates by the local **date**, which does
not change when 03:00 repeats. A footer `03:13` can therefore follow `03:43`
on successive frames without a clock error. The exact rendered text is an
inference from the tested code and fresh sensor readings, not a field in
these logs.

The implementation is a conversion, rather than a scheduled clock-setting
job:

1. `apps/firmware_esp32/main/main.c` composes `time_zone_eu(120)`.
2. `core/domain/civil_time.c:transition_ms()` calculates the last Sunday of
   March and October for the UTC instant's year, at minute 60 (01:00 UTC).
3. `time_zone_offset_min()` returns 180 minutes from the March transition
   inclusive to the October transition exclusive, otherwise 120.
4. `civil_time_local()` adds that offset. `view_model.c` converts the
   measurement's UTC timestamp when building `updated HH:MM`. The RTC and
   ESP32 system clock remain in UTC. The SNTP callback only sets UTC.

No previous-offset flag, internet lookup or special execution at 01:00 is
needed. A boot after the transition also calculates the correct offset.
Sensor deadlines, BSEC input times and reporting intervals use monotonic
time, so the repeated local hour does not repeat an hour's measurements.
CSV timestamps and debug prefixes remain UTC and unambiguous.

**Without a network**, a running board keeps UTC on the ESP32's system
clock and calculates the same offset. After a cold boot it gets UTC from
the PCF8563, if valid, then does the same conversion. The powered RTC's
measured drift above is not a calibration of the running ESP32's clock or
of the backup-powered RTC. If the RTC has no valid time and no system time
was retained across a reset, offline operation has no date to convert:
the footer stays `--:--` until time is supplied, for example by `time_set`.
The rule is compiled into the firmware; changes to the civil-time policy
would require changing its configuration/code.

**The screen is not a ticking clock.** No redraw is requested just because
the UTC offset changes. `updated HH:MM` records when the displayed values
were updated and remains on the glass until a sensor/status/user-triggered
redraw. This is ADR 0023's intended behaviour. A literal immediate
`03:59 -> 03:00` on the glass was not observed and should not be claimed.

Existing host tests `test_civil_time` and `test_view_model` exercise this
exact 2026 boundary without SNTP or Wi-Fi, including footer `03:59` then
`03:00`. The real board ran through it **online**; a board test with the
network disconnected across the transition remains to be done.

## USB MSC and retention while the card is unavailable

Checked `card_writer.c`, `log_tee.h`, `log_ring.c`, `recorder.c` and
`log_file.c` against [ADR 0036](../adr/0036-the-card-as-a-usb-disk.md):

- MSC flushes and closes files and unmounts the firmware's filesystem before
  handing sectors to the PC. The firmware does not write files concurrently
  with the PC. Sensors, the display and MQTT continue operating.
- **Debug records keep accumulating in the PSRAM ring**. Once the card is
  mounted again, the writer drains it into the daily log in append mode.
  Times are reconstructed from each record's monotonic age; crossing
  midnight can send retained records to the previous day's log. Session
  entries are consequently absent from a copy taken while MSC is still
  active; they become visible after return and a later copy.
- **CSV measurements are dropped during the session**, about 32 rows/min
  across both sources. Their event queue is still consumed; it is not kept
  for replay after mounting. Recording resumes in new `_N` files, leaving
  a gap. This applies to planned card absence too.
- The debug ring is fixed at **1,024 records × 320 bytes = 320 KiB**.
  When full, it keeps the oldest records and counts/discards new ones;
  after return it writes a loss notice. Available time depends on the
  initial occupancy and subsequent logging rate, not on all free PSRAM.
  Unplanned reset/power loss destroys the RAM backlog. Abrupt card removal
  may additionally lose records/buffered file data already being written;
  clean MSC entry does not have that removal race.

For the latest boot, excluding its first five minutes, observed windows of
1,024 normal log records span **3.65–7.89 hours**. October 24's 4,306
records/day imply **5.7 hours** for an initially empty ring at that average
rate. Quiet complete UTC hours have about 126–154 records/hour. These
figures estimate normal INFO logging, not a guaranteed minimum under error
bursts, repeated interaction or DEBUG verbosity. With `U` occupied slots
and rate `R` records/hour, the approximate remaining capacity is
`(1024 - U) / R` hours. `rec` reports ring occupancy, high-water mark,
overflow and per-source dropped-row counters after return to the console.

The October 23 log contains 13 completed MSC sessions; their intervening
entries are present in the later SD log, providing board evidence of
backlog recovery. For example, the 60.77 s session at 11:01:25–11:02:26Z
retains its debug entries while recording reports `state=no_medium`.
The longest of those sessions is 160.85 s. They do not test filling all
1,024 slots over hours in MSC.
